Each GPU holds 1/p of every weight matrix and does 1/p of every GEMM. Column split yields disjoint output slices; row split yields partial sums that must be added across GPUs.

This slide is the whole mechanism. Column-parallel: Y = X[W₀|W₁] = [XW₀|XW₁] — outputs are disjoint slices, no comm needed yet. Row-parallel: X split column-wise times W split row-wise gives X₀W₀ + X₁W₁ — each GPU has a full-shaped but PARTIAL result; summing across GPUs is literally the definition of all-reduce. Megatron's genius is sequencing these two so communication happens only once per block — next slide.
Megatron's Choreography

Column-split, then row-split: one all-reduce per block.

  • MLP: Y = GeLU(X·A)·B — split A by columns (GeLU applies locally, no comm!), B by rows → one all-reduce at the end
  • Attention: heads are already independent — shard heads across GPUs; the output projection is row-split → one all-reduce
  • Total: 2 all-reduces forward + 2 backward per Transformer layer

Why the order matters: column-first keeps the nonlinearity local. Row-first would need a sync before GeLU. Sequence parallelism upgrades this: swap each all-reduce for reduce-scatter + all-gather and shard the LayerNorm/dropout activations too.

cite: Shoeybi et al. 2019 (Megatron-LM) · Korthikanti et al. 2022 (sequence parallelism)
The exam-grade detail: GeLU(X·A) is elementwise, so if each GPU holds complete columns of X·A, it can apply GeLU without talking to anyone. That's why A is column-split. B is then row-split so its input (the column-sharded GeLU output) is already in the right layout — one all-reduce after B, done. Google-stack contrast worth dropping: in JAX you don't hand-write this — GSPMD/XLA inserts the collectives from sharding annotations.
The Collectives Zoo

Five verbs cover 95% of distributed ML.

CollectiveSemanticsCanonical ML use
Broadcastone rank's tensor → everyoneinitial weight sync
All-gathereveryone's shard → everyone (concat)FSDP param gather before a layer
Reduce-scattersum all, each rank keeps 1/pZeRO gradient sharding
All-reducesum all, everyone gets the totalDP gradients · TP partial sums
All-to-allrank i's j-th shard → rank jMoE expert routing

The identity to recite: all-reduce = reduce-scatter + all-gather — same total bytes, and splitting it is exactly how sequence parallelism and ZeRO find their savings.

Implemented by NCCL on GPUs. Don't confuse collectives with in-model tensor ops: pooling aggregates WITHIN one tensor on one device (part of the model's math); all-reduce aggregates ACROSS devices (invisible to the model, same result as single-GPU). Masking isn't aggregation at all — it excludes positions (causal/padding masks). Same reduction semantics (sum/max), totally different layer of the stack.
How All-Reduce Actually Runs
2 · (p−1)/p · n bytes per GPU
Ring all-reduce: p−1 reduce-scatter steps + p−1 all-gather steps, each moving n/p bytes. Bandwidth-optimal — cost per GPU is ~2n regardless of cluster size.

Each GPU only ever talks to its two ring neighbors, so every link runs at full tilt simultaneously. Popularized for ML by Baidu, then Horovod; it's what NCCL picks for large messages.

Walkthrough for p=4: chunk the tensor into 4. Reduce-scatter phase: 3 steps of "send one chunk to the right neighbor, add what arrives" — after 3 steps each GPU holds the fully-summed version of one chunk. All-gather phase: 3 more steps circulating the finished chunks. Total: each GPU sent 6 chunks of n/4 = 1.5n ≈ 2(p−1)/p·n. The magic: per-GPU traffic is independent of p — perfectly scalable in bandwidth. The catch is latency: 2(p−1) sequential steps — next slide.
The Cost Model Interviewers Love

T(message) = α + β·n — latency plus bandwidth.

Ring

T ≈ 2(p−1)·α + 2((p−1)/p)·β·n

Bandwidth-optimal, but latency grows linearly in p. Wins for big tensors.

Tree

T ≈ α·log p + (worse β term)

Latency-optimal. Wins for small tensors and giant p. NCCL switches automatically by size.

Pipelined tree

Chunk the message and stream it: broadcast drops from O((α+βn)·log p) to O(α·log p + βn) — the βn term stops paying the log p tax.

One sentence of α-β analysis turns "we use all-reduce" into a staff-level answer.

α = per-message startup latency (µs-scale: software + link latency), β = seconds per byte (inverse bandwidth), n = bytes, p = ranks. The pipelined-broadcast result is the one from Elizabeth's screenshot: non-pipelined tree sends the WHOLE message down log p levels → (α+βn)log p; pipelining streams chunks so transmission overlaps across levels → α·log p + βn. Same trick as pipeline parallelism itself — micro-batching a message. Nice callback to make explicitly in an interview.
Why TP Stays Inside the Node

TP communicates per layer. PP communicates per stage. That's the whole placement rule.

TP traffic

2 all-reduces of batch × seq × hidden per layer, every layer, forward and backward — and compute waits on them. Needs NVLink's 900 GB/s → TP degree ≤ 8, inside one node.

PP traffic

One activation tensor per micro-batch at each stage boundary, point-to-point. Survives 400 Gb/s InfiniBand → PP crosses nodes.

Cluster recipe: TP=8 inside the node · PP across nodes · DP/ZeRO across replicas = 3D parallelism.

Worked number: Llama-70B-ish layer, batch 8 × seq 4096 × hidden 8192 in BF16 ≈ 0.5 GB per activation tensor; two all-reduces per layer × 80 layers × fwd+bwd — this traffic is why 64 GB/s PCIe would strangle TP but 900 GB/s NVLink doesn't. Also mention comm/compute overlap: modern stacks fuse the all-reduce into the GEMM epilogue or overlap with the next kernel (async TP). TPU contrast: ICI mesh bandwidth is uniform across a pod, so the in-node/cross-node cliff mostly disappears — sharding choices differ.
