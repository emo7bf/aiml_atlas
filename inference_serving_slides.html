The two SLO words to use from sentence one: TTFT (time to first token — prefill's metric) and TPOT (time per output token — decode's metric). Every technique in this deck optimizes one without wrecking the other.
The Fault Line

Prefill is compute-bound. Decode is bandwidth-bound. Everything follows.

Prefill (the prompt)

All n prompt tokens processed in parallel — big GEMMs, tensor cores saturated. Compute-bound, like training. Metric: TTFT. One 100k-token prompt ≈ seconds of pure math.

Decode (the generation)

One token at a time: read all weights + whole KV cache to produce one token. Memory-bandwidth-bound, arithmetic intensity ≈ 1. Metric: TPOT. Ceiling: tokens/sec ≈ BW ÷ bytes-read.

Roofline callback: prefill lives on the compute roof, decode on the bandwidth slope. Batching moves decode toward compute-bound — which is why throughput serving is a batching game.

Why decode is intensity≈1: each weight is read once and used for one multiply-accumulate per sequence. Batching B sequences reuses each weight B times → intensity B → at B≈300 (H100's FLOPs/byte ratio) decode finally becomes compute-bound. That single piece of arithmetic explains continuous batching's existence.
The Scheduler

Batch at the token level, not the request level.

Continuous batching (Orca, OSDI '22)

Recompose the batch every decode step: a finished sequence's slot is instantly refilled by a waiting request. No padding, no waiting for the slowest sequence. 2–10× throughput; in every modern engine.

Chunked prefill

A 100-page paste would freeze everyone's decode for seconds. Split its prefill into chunks, interleave with decode steps — TPOT protected, TTFT for the big prompt slightly worse. The right trade.

Together these are the default modern scheduler: token-level batches mixing decode steps + prefill chunks, rebuilt every iteration.

Interview phrasing: "static batching has head-of-line blocking in two dimensions — across requests (batch waits for slowest) and within a request (giant prefill blocks everyone). Continuous batching fixes the first, chunked prefill the second." Orca is the citation; vLLM/TRT-LLM ('in-flight batching')/SGLang all implement it.
The KV Cache Is the Working Set

Page it like memory. Share it like a filesystem.

PagedAttention (vLLM)

KV cache in fixed-size blocks with an indirection table — no contiguous reservation, no fragmentation → denser batches → throughput. OS virtual memory, reinvented for attention.

RadixAttention (SGLang)

Organize cached blocks in a radix tree by token prefix: shared system prompts, few-shot headers, and agent-tree branches reuse KV automatically → TTFT ≈ 0 for the shared part.

Both are OS ideas crossing into ML systems — paging and prefix trees. Saying that out loud is free interviewer goodwill.

Numbers to attach: KV cache for a 70B GQA model ≈ 0.3–0.6 MB per token (precision-dependent) — a 32k-context conversation is ~10–20 GB, which is why fragmentation mattered enough to invent paging. Prefix caching shines in agents: a tree of tool-use branches shares the long trunk; only the leaves pay prefill.
Separate the Phases Physically

Prefill pools and decode pools: the p99 architecture.

  • Problem: colocated prefill bursts inflate decode tail latency — p99 TPOT spikes whenever a long prompt lands
  • Disaggregation: prefill nodes (compute-optimized, maximize TTFT throughput) and decode nodes (bandwidth/KV-capacity-optimized) — KV cache shipped between pools over NVLink/RDMA
  • Cost: the KV transfer itself + capacity planning for two pools; worth it at scale, overkill for one node
  • Cite: Splitwise (Microsoft), DistServe (2024); NVIDIA Dynamo productionizes the pattern
The L5 framing: chunked prefill and disaggregation solve the SAME interference problem at different scales — chunked prefill time-slices one pool (simple, some TTFT cost), disaggregation space-partitions two pools (hardware-matched, pays KV shipping). Choosing between them based on fleet size is the judgment answer. KV transfer math: a 10k-token prefill's cache ≈ 3–6 GB → sub-100ms over NVLink, so the transfer is affordable.
Spending Compute to Buy Bandwidth
draft k, verify in 1 pass
A small draft model guesses k tokens; the target model validates all k in one parallel forward — one weight-read now yields up to k tokens.

Speculative decoding gives 2–2.5× decode speedup with provably identical output distribution (rejection sampling keeps the target model's probabilities exact). It works because decode has idle compute to burn — the roofline gap is the budget. Cite Leviathan et al. 2023 (Google) & Chen et al. 2023 (DeepMind).

Mechanism worth narrating: accept draft token i with prob min(1, p_target/p_draft); on first rejection, resample from the adjusted distribution — expectation exactly matches the target model (the proof is 4 lines; knowing it exists is enough). Acceptance rate drives everything: ~70-80% typical; drops on hard/unusual text — so speedup is content-dependent. Variants: Medusa (extra heads), EAGLE (current SOTA drafting), n-gram lookup (free wins on copy-heavy tasks like code edits).

The One-Breath Answer

"Serving splits at the prefill/decode fault line — compute-bound TTFT vs bandwidth-bound TPOT — so you batch continuously at the token level, chunk big prefills or disaggregate the phases onto separate pools, page and prefix-share the KV cache, quantize the weights, and spend decode's idle compute on speculative drafts — each lever mapped to the phase whose SLO it protects."

🎛 Interactive · Batching Regime Finder

Slide the batch until decode goes compute-bound.

Decode intensity ≈ batch size. Below the chip ratio (~300 for H100 BF16) you're paying for ALUs that idle; above it, batching has bought back the compute roof.

Connect out loud: batch 1 → 0.3% ALU utilization (why single-stream decode is pure bandwidth), batch 64 → ~21%, batch 300+ → compute-bound (prefill-like). Continuous batching exists to keep real traffic near the high end of this slider.
