Opening frame: data parallelism scales the BATCH; pipeline parallelism scales the MODEL. When one GPU can't hold the weights + optimizer state + activations, you must split the model itself — by depth (pipeline) or by width (tensor parallel). This deck is the depth story.
Why It Exists
16 bytes / parameter
Adam mixed-precision training cost: 2 (weights) + 2 (grads) + 4+4+4 (FP32 master copy, momentum, variance)

A 70B model → ~1.1 TB of state, vs 80 GB of HBM on an H100. No single device survives this. Something must be split: the optimizer state (ZeRO/FSDP), the layers (pipeline), or the matrices (tensor parallel).

This memory arithmetic is the single best way to open any answer about model parallelism — it proves the need before describing the mechanism. 16 bytes/param is for Adam in mixed precision; inference is just 2 bytes/param (FP16) or 1 (FP8), which is why inference fits where training doesn't.
The Naive Version Fails

Put layers 1–8 on GPU 0, layers 9–16 on GPU 1... and watch utilization hit 1/p.

forward backward idle

With one batch and 4 stages, each GPU works 1/4 of the time. You bought four GPUs to get the throughput of one.

Vocabulary: this is "naive model parallelism" or "vertical model parallelism without pipelining." The dependency chain forces serialization: stage 2 can't start until stage 1 finishes the whole batch. Interviewers often start here and ask "how do you fix the idleness?" — the answer is the next slide.
The Fix — GPipe (Google, 2019)

Slice the batch into micro-batches; stages work on different slices simultaneously.

forward Fᵢ backward Bᵢ bubble

GPipe schedule: all forwards, then all backwards. Gradients from micro-batches accumulate — mathematically identical to the full batch.

Cite: "GPipe: Efficient Training of Giant Neural Networks using Pipeline Parallelism" — Huang et al., Google, NeurIPS 2019. The diagram shows p=4 stages, m=4 micro-batches. Note the gray triangles at the start (fill) and end (drain) — that's the bubble. Also note: micro-batching is just gradient accumulation distributed across stages; batch-norm is the one op it breaks (GPipe handles it specially; most Transformers use LayerNorm so nobody cares).
The Formula To Recite
bubble = (p − 1) / (m + p − 1)
p = pipeline stages · m = micro-batches

p = 8, m = 32 → 7/39 ≈ 18% wasted. Push m to 128 → ~5%. The bubble is an Amdahl's Law serial fraction: amortize it with more micro-batches — until activation memory or tiny-kernel inefficiency bites back.

Derivation worth knowing: the pipeline takes (m + p − 1) slots to do m slots of useful work per stage; the extra (p − 1) is fill + drain. Trade-off to volunteer: bigger m shrinks the bubble but (a) GPipe-style scheduling holds more in-flight activations and (b) smaller micro-batches mean smaller GEMMs that utilize the GPU worse — there's a sweet spot, not a free lunch.
The Memory Problem → 1F1B

GPipe hoards activations for all m micro-batches. 1F1B caps it at p.

GPipe schedule

All forwards first → every stage holds activations for m micro-batches before any backward frees them. Memory grows with m — exactly the knob you wanted to crank.

1F1B schedule

After warm-up, each stage alternates one forward, one backward. In-flight activations capped at ≤ p micro-batches. Same bubble fraction. From PipeDream; what Megatron-LM ships.

Plus activation checkpointing: drop intermediates, recompute in backward — ~33% more compute for an order of magnitude less activation memory.

This GPipe→1F1B progression is the classic interview arc: name the problem with the simple schedule (activation memory scales with m), then name the fix (1F1B keeps bubble identical but caps memory). PipeDream's original async version let stages run on stale weights (weight stashing) — modern synchronous training uses "PipeDream-Flush" / 1F1B. Checkpointing was in GPipe from day one; they called it re-materialization.
Shrinking the Bubble Further
  • Interleaved stages — each GPU holds several non-contiguous layer chunks (Megatron "virtual pipeline"): bubble ÷ v, at the cost of v× more communication
  • Zero-bubble schedules — split backward into input-grad vs weight-grad passes and slot the pieces into idle gaps (ZB-H1/ZB-V)
  • DualPipe — DeepSeek-V3 feeds micro-batches from both ends of the pipeline and overlaps comm with compute: near-zero bubble

The arc to narrate: GPipe (2019) → 1F1B → interleaved → zero-bubble (2023–24). Each step buys utilization with scheduling complexity.

The key insight behind zero-bubble: backward is really TWO computations — dL/d(input), needed urgently by the upstream stage, and dL/d(weights), which can wait. Decoupling them gives the scheduler flexible filler work. DualPipe is a great recency signal: DeepSeek-V3 technical report (Dec 2024), bidirectional pipeline + full comm/compute overlap, part of their famously cheap training run.
Why PP Crosses Nodes and TP Doesn't

Pipeline parallelism is the cheapest talker in the parallelism family.

What PP sends

One activation tensor, point-to-point, per micro-batch, per stage boundary. Hidden-size × micro-batch bytes. Tolerates slow links → runs fine over InfiniBand across nodes.

What TP sends

All-reduces inside every layer (two per Transformer block, via NCCL). Needs NVLink-class bandwidth → stays inside a node.

Standard cluster recipe: TP within the 8-GPU node, PP across nodes, DP across replicas — "3D parallelism."

This slide answers the L4+ follow-up "how do you decide which parallelism goes where?" The answer is pure bandwidth arithmetic: TP communicates activations per-layer collectively (needs 900 GB/s NVLink), PP communicates once per stage boundary point-to-point (fine at 400 Gb/s InfiniBand). Google-stack equivalent: on TPUs, GSPMD/XLA handles sharding and the ICI mesh changes the trade-offs — TPU pods favor more TP-like sharding because ICI is uniform.

The One-Breath Answer

"Pipeline parallelism splits layers into stages on different GPUs, streams micro-batches through to keep all stages busy, and eats a bubble of (p−1)/(m+p−1) idle time — which we shrink with more micro-batches, 1F1B scheduling, interleaving, and zero-bubble tricks — in exchange for the cheapest communication profile of any model-parallel scheme."
