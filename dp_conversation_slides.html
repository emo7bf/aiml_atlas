First · The Words on the Whiteboard

Naming conventions — so the vocabulary never rattles you.

You'll seeIt means
dp, dp[i], dp[i][j]THE table — yes, your instinct is right: dp is the state array; dp[state] holds that subproblem's answer. The name is literally short for "dynamic programming." Out loud, call it "the table."
memo, cachethe dictionary used by top-down (memoized) solutions — same answers as dp, filled lazily by recursion instead of a loop
@cache / @lru_cachePython's built-in memoizer — a decorator that gives any function a memo for free
f(i), OPT(i)textbook/paper notation for the same idea as dp[i] — MIT's SRTBOT lectures write subproblems as functions
i, j, k · n, m · Wstate indices · input sizes · a budget/capacity. Rule: say what each letter means in English before using it
state spacethe set of ALL states; its size × transition cost = your runtime
recurrence / transitiontwo names, one formula — how small answers combine into bigger ones
top-down / bottom-up= memoization / tabulation — the two dialects, same language
The dp-is-the-table confirmation is deliberate — she asked. Worth adding verbally: in interviews ANY clear name works (best, ways, cost) as long as you state the meaning; dp[] is just the lingua franca of editorial solutions. OPT() appears in Kleinberg-Tardos; f() in Demaine.
Toy One · Stepping Stones

Six stones. Steps of +1 or +2. How many ways across?

Six stones, 0 → 5. Steps of +1 or +2. No rush at all. Finish this sentence: dp[i] = …
…say your sentence before advancing. (A value, not a decision — remember the heist.)
dp[i] = the number of distinct ways to reach stone i. A value — something a smaller version of the question hands back.
Now the transition. Stand on stone i, look backward: what was the very last step that landed you here?
It came from i−1 (rose arcs) or i−2 (indigo arcs). No other doors exist. So dp[i] = dp[i−1] + dp[i−2] — watch each stone get fed by exactly its two:
Housekeeping: bases? order? space?
dp[0] = 1, dp[1] = 1 · order: left→right (dependencies ready before use) · space: each stone looks only 2 back → keep a window of two variables, O(1), not the whole pond.
The arcs ARE the recurrence this time — rose = the +1 step, indigo = the +2 step, drawn into each stone as its count appears. This replaces the old misrepresenting frog: now the animation shows ALL incoming options, which is exactly what the sum means. Counts: 1,1,2,3,5,8.
Toy Two · Market Day (where instinct fails)

Mango tokens worth 1, 3, and 4. Pay exactly 6 — fewest tokens.

Tokens: 🪙1 · 🪙3 · 🪙4. You owe exactly 6. Instinct says biggest token first. Indulge it — what does greedy pay?
…work greedy by hand before advancing: take 4, then what?
Greedy: take 4 → owe 2 → no 2-token exists → 1 + 1. Total: three tokens (4+1+1). Feels fine, doesn't it.
Can you beat three? Sit with it.
3 + 3 = 6. Two tokens. Greedy lied — politely, confidently, the way it always does.
This is the moment DP earns its existence. The best first choice ≠ part of the best whole. DP refuses to trust any single choice — it asks every amount what its best answer is, and builds only on proven answers.
Coins {1,3,4}, amount 6 is the canonical minimal greedy-failure example. If probed "when IS greedy safe?": canonical coin systems (like US coins) have the greedy-choice property; proving it is nontrivial — which is exactly why DP is the default and greedy needs justification. This slide is the 'prove the need' beat she asked for.
Toy Two · Solved, Calmly

Every amount gets its own answer. Watch them earn it.

Our five questions. State — one sentence.
dp[a] = the fewest tokens that pay exactly amount a.
Transition: condition on the last token you hand over.
Last token = c ⇒ before it you owed a−c, paid optimally. dp[a] = 1 + min over c of dp[a−c] · dp[0] = 0 · order: amounts ascending ⤵
# tabulated — your preferred dialect, and the right one here
def fewest_tokens(tokens, amount):
    INF = float("inf")
    fewest = [0] + [INF] * amount          # BASE: amount 0 costs 0 tokens
    for owed in range(1, amount + 1):       # ORDER: every amount, ascending
        for c in tokens:
            if c <= owed:
                fewest[owed] = min(fewest[owed], 1 + fewest[owed - c])
    return fewest[amount]

fewest_tokens([1, 3, 4], 6)   # -> 2   (3 + 3 — the answer greedy never saw)
Note the ascending loop: tokens are reusable, so today's row may feed itself — the Garden's knapsack ran descending for exactly the opposite reason.
dp strip: [0,1,1,1,2,2,2] for amounts 0..6 — dp[6]=2 highlighted rose. The ascending-vs-descending callback to the Garden's Rep 5 is the deliberate thread: reuse allowed → ascending (coin change); use-once → descending (0/1 knapsack).
Strategy & Staging · Choosing Your Dialect

Memoize or tabulate? Here's the honest decision rule.

You tend to tabulate. Good default. Let's make the reasons yours again — and name when the other dialect wins.
Tabulation wins because: ① no Python recursion limit (~1000 frames) ② the order is explicit — dependency bugs surface honestly ③ space-optimization is natural (keep the window: two variables, one row) ④ plain loops are fast & cache-friendly.
Memoization wins when: ① the state space is huge but sparsely visited (cache computes only what's needed) ② the filling order is hard to see — intervals, trees, digit DP (Part 3 territory) — recursion finds the order for you.
And the staging, live in the room:
The staircase, every time: ① restate + tiny example → ② brute recursion aloud → ③ point at the overlap → ④ memoize (correctness first) → ⑤ convert to a table, narrating order → ⑥ shrink to the window → ⑦ complexity = states × transition.
