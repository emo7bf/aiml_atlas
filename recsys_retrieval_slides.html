The Shape of Every RecSys

Cost per item rises; candidates shrink. That's the whole design.

Corpus · ~10⁹ itemsembeddings precomputed offline
Retrieval · ~10³ candidatesdot product vs ANN index · microseconds/item
Ranking · ~10² scoredheavy model, cross features · milliseconds/item
Re-rank · ~10 showndiversity, freshness, policy, business rules

Each stage trades recall (don't lose the good stuff) for precision (order it right) at rising cost. Frame every RecSys answer around this funnel before diving anywhere.

The one-liner that earns the slide: "retrieval is optimized for recall@k, ranking for precision/NDCG." Also note the latency budget framing: the whole funnel typically runs in ~100–300ms; retrieval gets maybe 10–20ms — which is WHY it must be a dot product against a prebuilt index and not a model forward pass per item.
Retrieval's Workhorse

Two towers, one dot product — and they never meet until serving.

user embedding u
MLP layers
user features
history, context, demographics
computed per-request
u · v
item embedding v
MLP layers
item features
id, metadata, content signals
precomputed offline → ANN index

The decoupling IS the point: relevance must reduce to a dot product so retrieval becomes nearest-neighbor search. The price: no user×item cross features — those wait for the ranking stage.

Interview trap: "why not use a single network taking (user, item) pairs?" — because then you'd need a forward pass per item per request; the two-tower factorization is what makes O(10⁹)-corpus retrieval possible. The dot-product constraint is a capacity sacrifice made for indexability. Cite Yi et al. 2019 (Google) for the two-tower + sampled-softmax formulation with logQ correction.
How the Towers Are Trained

Softmax over 10⁹ items is impossible — so you sample, then correct.

In-batch negatives

Other items in the batch are the negatives — free, since their embeddings are already computed. The catch: popular items appear (as negatives) far too often.

logQ correction

Fix the popularity skew: subtract log Q(item) (its sampling probability) from each logit. Skipping this silently punishes popular items. This detail is the senior tell.

Hard negatives

Mine near-misses from the ANN index itself — items the model almost retrieves. Sharpens the decision boundary; overdo it and training destabilizes.

Loss family: sampled softmax / InfoNCE-style contrastive — the same mathematics as CLIP.

Why logQ: in-batch sampling draws negatives ∝ item popularity, not uniformly, so the effective softmax is biased; subtracting log Q(i) from the logit makes the sampled softmax an unbiased estimate of the full softmax (importance correction). One more production wrinkle worth voicing: the training objective (clicked/watched) is a PROXY for the business goal — feedback loops (training on your own recommendations) and position bias contaminate labels; log-and-learn systems correct with propensity weighting.
Serving: Nearest Neighbors at Scale

ANN search: trade a point of recall for 1000× the speed.

Index familyIdeaTrade-off
IVF-PQ (FAISS)cluster the space; quantize vectors to bytestiny memory, lossy distances
HNSWnavigable small-world graph, greedy descentfast & accurate, memory-hungry, hard to update
ScaNN (Google)anisotropic quantization — penalize error in the direction that changes dot-product rankingsthe one to name at Google

Measure with recall@k vs QPS curves. Exact brute force is actually fine to ~1M vectors on a GPU — know when you don't need an index at all.

ScaNN's insight (Guo et al., ICML 2020): standard quantization minimizes ‖v−ṽ‖² uniformly, but retrieval only cares about errors parallel to likely query directions — anisotropic loss weights the components that flip rankings. SOAR (2023) is the recent upgrade. The "1M vectors → brute force on GPU" point is a great judgment signal: 1M × 128-d dot products ≈ 128 MFLOPs ≈ microseconds on an H100 — don't build infrastructure you don't need.
The Operational Slide (The L5 Gap)

Indexes go stale. Towers drift. Versions must match.

  • Batch rebuild: re-embed the corpus + rebuild the ANN index every N hours — simple, but new items are invisible until the next build
  • Fresh buffer hybrid: big static index + small brute-force buffer of new items, merged at query time — the standard answer for "how do new videos get recommended?"
  • Version skew: the user tower and the index must come from the same model version — mixing embedding spaces silently breaks retrieval. Deploy towers + index atomically
  • Embedding drift: retrain → whole corpus must be re-embedded; incremental training mitigates but complicates
This slide is verbatim the feedback gap: "real-time index updates vs batch retraining." The fresh-buffer answer: new items' embeddings computed on upload by the item tower, held in an unindexed brute-force pool (cheap while small), merged into candidates at query time, folded into the main index at next rebuild. Version skew is the production bug interviewers love: user embedding from model v7 against an index built with v6 = garbage retrieval with no errors thrown. Say "atomic swap of tower + index" and you sound like you've been paged for it.
After Retrieval: The Ranking Stage

Ranking is where the cross features live — and where the memory monsters sleep.

Why a second model

Two-tower can't express user×item interactions ("this user × this topic at night"). The ranker sees the full joint feature set — Wide & Deep (Google 2016), DCN, DLRM — on only ~10² candidates, so it can afford to be heavy.

The hardware tie-in

Production rankers hold terabyte-scale embedding tables (one row per user/item/feature value) — sharded across devices as model parallelism for memory, not compute, with all-to-all lookups. Your parallelism decks apply directly here.

Judge it with NDCG/AUC offline — but trust only the online A/B: position bias and feedback loops routinely fake offline wins.

The embedding-table point bridges this deck to the systems decks: DLRM-style models are memory-bandwidth-bound on lookups (sparse, random access — the GPU's weak spot from deck 1!) which is why Meta/Google built custom sharding and why recommendation inference often lives on CPUs + custom accelerators. Full-circle moment worth making out loud in an interview.

The One-Breath Answer

"Retrieval at scale is a funnel: a two-tower model maps users and items into one embedding space trained with sampled softmax plus logQ correction, item embeddings live in an ANN index like ScaNN — kept fresh with batch rebuilds plus a brute-force buffer, versioned atomically with the tower — and the survivors go to a heavy cross-feature ranker, validated offline by recall@k and NDCG but trusted only after an online A/B."

🎛 Interactive · Brute Force or Index?

The 30-second math that decides if you need ANN at all.

1M vectors? Brute force on a GPU and skip the infrastructure. 1B at 1k QPS? That's the ANN industry's reason to exist. Slide between the regimes.

Rehearsal: set 10⁹ items, 128 dims, 10⁵ QPS — the YouTube case: ~256 GFLOPs/query, tens of PFLOP/s fleet-wide, 512 GB of raw embeddings. No. Then 10⁶ items at 100 QPS: 0.26 GFLOPs/query — a single GPU shrugs.
