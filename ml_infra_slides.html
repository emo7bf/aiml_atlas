The Big Three

Imperative, functional, or legacy-production: pick by regime.

PyTorch

Eager define-by-run autograd; torch.compile bolts a compiler on after the fact. The research default and ecosystem king. Distributed = DDP/FSDP over NCCL.

JAX (the Google one)

Pure functions + composable transforms: grad · jit · vmap · shard_map. Compiles through XLA; sharding by GSPMD annotation. How TPUs are programmed; how Gemini was trained.

TensorFlow

Graph-first heritage, now eager + tf.function. Fading in research, entrenched in production estates — TF Serving, TFLite (edge), TFX (Google's pipeline lineage).

The judgment sentence: "PyTorch for ecosystem, JAX for Google-stack and TPUs, TF where it's already deployed."

JAX depth for a Google room: functional purity is WHY the transforms compose — jit(vmap(grad(f))) works because f has no hidden state; PRNG keys are explicit for the same reason. The trade: in-place mutation and dynamic shapes are awkward (recompilation on shape change). PyTorch's counter-evolution: torch.compile/Dynamo captures graphs from eager code — both frameworks converged on 'trace Python → compile with a backend' from opposite ends.

The Disambiguation Trap

There are two Tritons. Asking "which one?" is a free senior point.

OpenAI Triton — the compiler

Python DSL for writing GPU kernels at the tile level. Lives at the bottom of the stack: it's what torch.compile generates. You use it to make one op fast.

NVIDIA Triton — the server

Multi-framework inference server: TensorRT/PyTorch/ONNX backends behind one gRPC endpoint, dynamic batching, model ensembles. Lives at the top of the stack: it's how models meet traffic. (TRT-LLM often runs as a Triton backend.)

One writes kernels; one serves models. They share nothing but the name — and conflating them is a known candidate screener.

If the interviewer says just "Triton," respond: "the kernel language or the inference server?" — instant signal you've touched both layers. Placement of Triton Server vs vLLM: Triton Server is the general-purpose answer (CNNs, rankers, ensembles, mixed fleets); vLLM/SGLang/TRT-LLM are LLM-specialized engines — and in practice TRT-LLM deploys behind Triton Server at NVIDIA shops.
Distributed Python

Ray: tasks for stateless work, actors for stateful — everything else is a library on top.

  • @ray.remote on a function → task (stateless, scheduled anywhere); on a class → actor (stateful, pinned process — a parameter server, a simulator, an engine)
  • Object store with zero-copy shared memory per node — large arrays pass by reference, not pickle
  • The library stack: Ray Train (distributed training), Tune (HPO at scale), Data (streaming ingest), Serve (model composition), RLlib
  • Who leans on it: OpenAI (training orchestration), vLLM (multi-node serving), Anyscale (the company)

The regime sentence: "Ray when I need to scale arbitrary Python; Spark when it's really ETL; Kubernetes alone when the units are services, not computations."

Tasks-vs-actors is the one mechanism to explain crisply if probed — it's just 'pure function vs object with state' distributed. Honest limitation to volunteer: Ray adds a scheduling/serialization layer — for a single-node job or a simple batch script, it's overhead without benefit. The 'don't reach for infrastructure you don't need' instinct from the RecSys deck applies verbatim.

Kubeflow Pipelines runs this as containers on Kubernetes; Vertex AI Pipelines is Google's managed flavor (the name to drop); TFX is the Google-internal ancestor; Airflow orchestrates anything but knows nothing about ML.

The evaluation gate is the step candidates forget — automatic blocking on regression (overall AND per-slice: new model better on average but worse for a user segment = don't ship). Slice-based eval is a very Google concern (fairness + long-tail users). Also say 'every step containerized and versioned → any model traceable back to exact data + code' — that's lineage, and it's the point of the whole apparatus.
The Data Layer

Vector DBs and feature stores: don't deploy infrastructure you don't need.

Vector databases

ANN (HNSW/IVF/ScaNN) + metadata filters + CRUD + replication. Ladder of commitment: pgvector (vectors in your existing Postgres) → Qdrant/Milvus (dedicated OSS) → Pinecone / Vertex AI Vector Search (managed; Vertex is ScaNN-backed — the Google name).

Feature stores

One feature definition served two ways: batch (training) and low-latency (serving). Exists to kill training/serving skew — the bug where offline and online compute the "same" feature differently. Feast (OSS), Vertex AI Feature Store (managed).

The pgvector-first argument: if you already run Postgres and have <10M vectors, adding a service (new infra, new failure mode, data sync) to avoid an extension is negative engineering. Training/serving skew example to have ready: 'user's 7-day click count' computed by a batch SQL job for training but by a streaming counter online — subtly different windows → silent accuracy loss. The feature store's whole job is making that impossible.
Keeping Models Alive

Models degrade silently: the world drifts, the model doesn't.

  • Experiment tracking — MLflow / Weights & Biases: every run's config, metrics, artifacts
  • Model registry — versioned, stage-gated artifacts (staging → prod); rollback is a pointer flip
  • Drift monitoring — compare live feature distributions vs training (PSI / KL divergence); watch proxy metrics while true labels lag
  • Retraining triggers — scheduled, drift-triggered, or performance-triggered; close the loop through the same gated pipeline

The MLOps interview sentence: "deploy is the midpoint, not the finish line — the design must say who notices when the model goes quietly wrong."

Label lag is the subtle point: for many systems (fraud, recommendations, churn) ground truth arrives days or weeks late — so you monitor input drift and proxy signals (prediction distribution shifts, calibration drift) in the meantime. Data drift vs concept drift distinction: inputs changed vs the input→label relationship changed; the second is invisible to input monitoring, which is why gated shadow evals and periodic relabeling exist.

The One-Breath Answer

"The stack is regimes, not brands: PyTorch for ecosystem, JAX-on-XLA for the Google/TPU path, Ray to distribute arbitrary Python, Triton Server (not the kernel DSL!) or an LLM engine to meet traffic, Kubeflow/Vertex Pipelines to make training a gated, versioned DAG, a feature store to kill training/serving skew, and drift monitoring because deploy is the midpoint — not the finish line."
