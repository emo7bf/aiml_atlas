Why a Second Dimension

When your English sentence "leaks," add an index — don't fight it.

The leak test (from Part 1)

Try: "dp[w] = best value within capacity w"… but the best value depends on which items are still available. The sentence leaks → the state is missing a dimension → "dp[i][w] = best value using only the first i items, within capacity w." Sealed.

The three 2-D families

▸ Grid walks — state = a cell (row, col)
▸ Budgeted choices — state = (items considered, budget left)
▸ Two sequences — state = (prefix of A, prefix of B)
Spot which family a problem belongs to and the state writes itself.

Complexity stays mechanical: states × transition — an m×n table with O(1) transitions is O(mn). Done before you code.

This slide is the bridge from the Part-1 pre-test miss ("whether to rob house i") to 2-D: the fix for a leaking state is ALWAYS to encode the leaked information as another index. The three-family taxonomy covers the large majority of interview 2-D DP; Part 3 handles the exotic states (intervals, bitmasks, tree nodes).
Family 1 · Grid Walks — Unique Paths (LeetCode 62)

"Robot moves only right/down. How many paths corner to corner?"

The recipe, run

1 · State: dp[r][c] = # paths reaching cell (r,c)
2 · Transition: last move was ↓ or →, so dp[r][c] = dp[r−1][c] + dp[r][c−1]
3 · Base: first row & column = 1 (one way: straight line)
4 · Order: row-major — exactly the order the cells appear ←
5 · answer bottom-right · O(mn) / O(n) with one row

The animation IS the lesson: cells appear in dependency order (each cell only after its up & left neighbors), teal frame first (base), indigo interior (computed states). Say it in an interview as "I fill in an order where dependencies are already resolved." Fun fact for bonus points: the answer is C(m+n−2, m−1) — a binomial coefficient — because a path is a choice of which steps go down. DP and combinatorics agree.
Grid Walks · Code + the Min-Cost Twin

Change the combiner, get a new problem. The table is the same shape.

# Unique Paths — counting: combiner is +
def unique_paths(m, n):
    row = [1]*n                              # base row; space-optimized to one row already
    for r in range(1, m):
        for c in range(1, n):
            row[c] = row[c] + row[c-1]        # up (old row[c]) + left (new row[c-1])
    return row[-1]

# Min Path Sum (LC 64) — optimizing: combiner is min, plus the cell's cost
def min_path_sum(g):
    m, n = len(g), len(g[0])
    row = list(itertools.accumulate(g[0]))   # base: first row = running cost
    for r in range(1, m):
        row[0] += g[r][0]
        for c in range(1, n):
            row[c] = g[r][c] + min(row[c], row[c-1])
    return row[-1]

Same state, same order, same O(mn) — only the combiner changed (+ → min). This is Part 1's counting-vs-optimizing split, now in 2-D. The one-row trick: row[c] still holds the up value right before you overwrite it.

The space optimization deserves narration in an interview: "each cell depends only on the row above and the cell to the left, so I keep one row; reading row[c] before assignment gives me 'up' for free." That sentence shows you understand the dependency window, not just the trick. Follow-up variant: Unique Paths II (obstacles) — set blocked cells to 0, base cases stop at the first obstacle.
Family 2 · Budgeted Choices — 0/1 Knapsack

"Items with weights & values, capacity 8. Maximize value."

items: A(w2,v3) · B(w3,v4) · C(w4,v5) · D(w5,v8) — rows = items considered, cols = capacity

The recipe, run

1 · State: dp[i][w] = best value from the first i items within capacity w
2 · Transition: last decision = item i in or out:
dp[i][w] = max(dp[i−1][w], dp[i−1][w−wᵢ] + vᵢ)
3 · Base: row 0 = 0 (no items, no value)
4 · Order: item by item   5 · dp[n][W] · O(nW)

Knapsack is THE archetype of "condition on the last decision" with a budget: every resource-allocation DP (coin change, partition, subset-sum, target-sum) is knapsack in costume. The O(nW) complexity is 'pseudo-polynomial' — polynomial in the VALUE of W, not its bit-length — a nice senior aside. The rose cells in the animation mark where 'take' beat 'skip'.
Knapsack · Code + the Famous Direction Bug

One row again — but now the loop MUST run backwards.

# 2-D (clear): dp[i][w] = max(skip, take)
def knapsack(items, W):                       # items = [(weight, value), ...]
    dp = [0]*(W+1)                            # one row: dp[w] = best value within capacity w
    for wt, val in items:
        for w in range(W, wt-1, -1):          # ← DESCENDING. The whole exam is this line.
            dp[w] = max(dp[w], dp[w-wt] + val)
    return dp[W]
  • Why backwards? dp[w−wt] must be the previous item's row. Ascending order overwrites it first → you'd reuse item i within its own row → you've accidentally solved unbounded knapsack
  • The flip side: unbounded knapsack / coin change wants exactly that reuse → loop ascending. One character of difference, two different problems
  • This is Part 1's bug #2 ("iteration order violates dependencies") in its most-asked costume
If an interviewer asks exactly one thing about knapsack, it's the loop direction. The clean mental model: descending = each item used ≤ once (reads come from yesterday's row); ascending = items reusable (reads come from today's). Coin Change (LC 322) is the ascending twin: dp[a] = min(dp[a], dp[a−coin]+1), loop ascending — worth writing in the playground tonight.
Family 3 · Two Sequences — Longest Common Subsequence

"ROBIN" vs "GOBLIN" — align two strings with one table.

The recipe, run

1 · State: dp[i][j] = LCS length of A's first i chars and B's first j chars
2 · Transition: condition on the last characters:
match → dp[i][j] = dp[i−1][j−1] + 1 (rose cells!)
else → max(dp[i−1][j], dp[i][j−1])
3 · Base: empty prefix rows/cols = 0
5 · dp[m][n] = 4 ("OBIN") · O(mn)

The rose diagonal cells are the character matches — watching them light up teaches the recurrence better than the formula. LCS is the gateway to the string-DP family: Edit Distance (LC 72) is the same table with three transitions (insert/delete/replace, each cost 1); diff tools and DNA alignment are this exact algorithm at industrial scale. 'Subsequence ≠ substring' is the definitional trap to pre-empt out loud.
The 2-D Bug List (Extends Part 1's)
  • Loop direction — the knapsack descending/ascending trap: decide reuse or not first, then pick the direction
  • Padding off-by-one — index dp by prefix length (size m+1×n+1 with a zero row/col), not by character index; kills most LCS bugs before they exist
  • Row/col swapped — say out loud which index is which ("i = items, w = capacity") and keep it; mixing them compiles fine and fails silently
  • State still leaking — if (i, j) isn't enough ("…but it depends whether I'm holding the stock"), add dimension #3; small extra dimensions (2–3 values) are cheap
  • Space-optimizing too early — write the clear 2-D version first; collapse to one row only after it's correct

Testing ritual, upgraded: trace a 2×3 table by hand before trusting any 2-D loop. Same discipline, one more index.

The "say which index is which, out loud" habit is both a bug-preventer and a communication score. Stock-problem preview (the dimension-3 example): dp[i][holding] — Best Time to Buy/Sell with cooldown/fees are 2-state machines over time, the gentlest introduction to added dimensions, good playground material after this deck.
The One-Breath Answer

"When the 1-D state sentence leaks, I add an index: grid walks take a cell, budgeted choices take (items, capacity), two sequences take (prefix, prefix) — the transition still conditions on the last decision, bases are the empty row and column, cost is still states × transition, and the table collapses to one row once I know the dependency window — looping backwards if each item may be used only once."
