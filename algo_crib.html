# binary search — the loop-invariant version (say the invariant out loud!)
def binary_search(arr, target):
    lo, hi = 0, len(arr) - 1          # invariant: answer (if any) lives in arr[lo..hi]
    while lo <= hi:                   # <= : a 1-element window still needs checking
        mid = (lo + hi) // 2
        if   arr[mid] == target: return mid
        elif arr[mid] <  target: lo = mid + 1   # mid is ruled out — always shrink!
        else:                    hi = mid - 1
    return -1                         # bisect_left/bisect_right do the boundary variants
"The input is sorted — that's a signal: binary search gives O(log n), or two pointers give O(n)." Sorted input should trigger this reflex before you design anything else.
The classic binary-search bug is an infinite loop from lo = mid (window never shrinks). Always mid ± 1 on the ruled-out side. And know bisect exists — using the standard library is a senior move, not a cheat.

2 · Divide & Conquer vs DP — you know this fork already

Split the problem, solve pieces recursively, combine. The recognition fork you already own: subproblems don't overlap → divide & conquer (mergesort's halves are disjoint); subproblems repeat → DP (your whole Garden). Canonical examples: merge sort, quicksort/quickselect (k-th element in O(n) average), binary search (D&C with one branch), closest pair of points.

For recurrences: "T(n) = 2T(n/2) + O(n) solves to O(n log n)" — knowing the mergesort recurrence cold covers 90% of D&C complexity questions; name-drop the Master Theorem for the general case.

# THE heap pattern: top-k largest in O(n log k) — keep a small min-heap of survivors
import heapq
def top_k(nums, k):
    heap = nums[:k]; heapq.heapify(heap)        # min-heap of the current k best
    for x in nums[k:]:
        if x > heap[0]:                         # beats the weakest survivor?
            heapq.heapreplace(heap, x)          # pop+push in one O(log k)
    return heap                                  # (or heapq.nlargest(k, nums) — stdlib!)
"A heap is the answer when I need repeated access to the best remaining item — top-k, merging k sorted lists, Dijkstra's frontier, schedulers." That sentence covers every heap question's opening.
A heap is NOT sorted — only the root is guaranteed. If you need full order, sort. If you need the k best of a stream, heap. heapify is O(n), a favorite trivia probe.

4 · Queues, Stacks, Deques highlighted

Queue (FIFO) → collections.deque, O(1) both ends — the engine of BFS (you tapped it in Night Sky ✦). Stack (LIFO) → a plain list (append/pop) — the engine of DFS, and recursion is an implicit stack. Deque → both at once; also the sliding-window-maximum trick (monotonic deque).

Never use list.pop(0) as a queue — it's O(n) per pop (everything shifts). deque.popleft() is the O(1) answer, and saying why is free credit.

# Dijkstra = BFS where the queue becomes a MIN-HEAP keyed by distance (lazy-deletion style)
import heapq
def dijkstra(graph, src):                        # graph[u] = [(v, weight), ...]
    dist = {src: 0}
    heap = [(0, src)]                            # (distance so far, node)
    while heap:
        d, u = heapq.heappop(heap)               # closest unfinished node
        if d > dist.get(u, float("inf")): continue   # stale entry — skip (lazy deletion)
        for v, w in graph[u]:
            nd = d + w
            if nd < dist.get(v, float("inf")):   # found a shorter way in
                dist[v] = nd
                heapq.heappush(heap, (nd, v))
    return dist

A* in one breath: identical loop, but the heap is keyed by d + h(v), where h estimates remaining distance. If h never overestimates ("admissible" — e.g., straight-line distance on a map), A* stays optimal and explores far less. Set h = 0 and A* is Dijkstra.

The ladder: "unweighted → BFS. Weighted, non-negative → Dijkstra. Have a goal + a geometric hint → A*. Negative edges → Bellman-Ford." Pick by the problem's shape, say the ladder out loud.
#1 Dijkstra mistake: using it on unweighted graphs (BFS is simpler and faster) or with negative edges (silently wrong). #2: forgetting the stale-entry skip in the heap version.

6 · NP-complete, in interview-sized portions

A problem where a proposed answer can be verified in polynomial time, but no polynomial-time solver is known — and all NP-complete problems reduce to each other, so cracking one cracks all. The guide's examples: traveling salesman, knapsack (its decision version). The delicious footnote you're equipped for: your 0/1 knapsack DP is O(nW) — pseudo-polynomial (polynomial in W's value, exponential in its bit-length), which is exactly how an NP-complete problem can still have a practical DP.

"This looks NP-hard — so I'd ask about constraints: small n → bitmask/brute force; small budget → pseudo-polynomial DP; otherwise greedy or approximation and I'd say so explicitly." Recognizing intractability and pivoting is the senior answer; grinding on an exact algorithm is the junior one.
