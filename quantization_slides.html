Framing thesis: quantization works because decode is memory-bandwidth-bound (roofline callback) — every bit you shave off the weights is read-bandwidth you get back. The interview-grade skill is knowing WHICH cost each method attacks: memory, bandwidth, or the matmul itself.
Why It's the Biggest Lever
tokens/sec ≈ BW ÷ weight-bytes
Autoregressive decode reads every weight per token. Halve the bits → double the ceiling. No other optimization has this slope.

70B model on one H100 (3.35 TB/s): BF16 = 140 GB — doesn't fit. FP8 = 70 GB → ~48 tok/s ceiling. INT4 = 35 GB → ~96 tok/s and room for KV cache. Quantization is simultaneously a capacity, bandwidth, and (sometimes) compute win.

The "sometimes compute" hedge matters: weight-only INT4 still dequantizes to FP16 for the matmul — bandwidth win only. Getting the actual MATH cheaper requires formats the tensor cores execute natively: FP8 on Hopper, INT8 (W8A8), FP4/MX on Blackwell. That distinction is slide 5's whole job.
The Precision Ladder

Each rung halves memory. The question is what breaks.

16-bit
BF16 / FP16 — the baseline, nothing breaks
8-bit
FP8 E4M3/E5M2 — needs per-tensor scaling (Transformer Engine)
8-bit
INT8 W8A8 — breaks on activation outliers → SmoothQuant
4-bit
INT4 weights — breaks naively → GPTQ / AWQ
4-bit
NF4 — QLoRA's fine-tuning format

FP8 comes in two flavors: E4M3 (precision) for weights & activations in the forward pass, E5M2 (range) for gradients in the backward — gradients are spiky and need exponent, not mantissa.

Bytes/param: 2.0 (BF16) → 1.0 (FP8/INT8) → 0.5 (INT4/NF4). The E4M3/E5M2 assignment is a favorite trivia probe — anchor it with "gradients need RANGE": their magnitudes swing orders of magnitude during training, while forward tensors are better behaved. Below 4-bit: FP4 + microscaling (MX) block formats on Blackwell — shared exponent per 32-value block.
Where It Breaks

The outlier-channel problem: a few activation channels are ~100× the rest.

The failure

INT8 has 256 levels. One 100× outlier channel forces the quantization scale to cover it → every normal channel gets crushed into a handful of levels. Weights are well-behaved; activations are the problem child (emergent in LLMs > ~6B params).

The fix: migrate the difficulty

SmoothQuant: divide activations by per-channel scale s, multiply matching weight columns by s — mathematically identical network, flatter activations, slightly lumpier weights (which tolerate it). Result: full W8A8 → real INT8 tensor-core matmuls.

Alternative lineage: LLM.int8() keeps outlier channels in FP16 via mixed decomposition; rotation methods (QuaRot) scramble outliers away with orthogonal transforms.

The emergent-outliers observation is from Dettmers' LLM.int8() paper (2022) — outlier channels appear consistently past ~6.7B params and carry disproportionate information; naively clipping them craters accuracy. SmoothQuant's elegance: it exploits the associativity (X/s)·(s·W) = X·W, pre-folding s into the weights offline so inference pays nothing. 'Migrate difficulty from activations to weights' is the phrase to say out loud.
Getting to 4-Bit

GPTQ compensates the damage; AWQ avoids doing it.

GPTQ — repair as you go

Quantize weight columns one at a time; use second-order (Hessian) info to adjust the not-yet-quantized weights to absorb each column's error. Descends from Optimal Brain Surgeon (LeCun-era lineage — cite it).

AWQ — protect what matters

Observation: ~1% of weight channels are salient — found via activation magnitudes, not weight magnitudes. Scale those channels up before quantizing (and inputs down to compensate) so the grid preserves them. No retraining, uniform INT4, hardware-friendly.

Both are PTQ — post-training, calibration-set only, minutes-to-hours. The contrast sentence: GPTQ fixes error after the fact with curvature; AWQ prevents error up front with saliency.

Follow-up interviewers like: "weight-only INT4 — where's the speedup?" Answer: memory capacity + bandwidth (weights stream 4× smaller), but the GEMM still runs FP16 after dequantization (fused into kernels like Marlin). So INT4 shines at small batch / decode (bandwidth-bound), while W8A8/FP8 shines at large batch / prefill (compute-bound). Mapping method → regime is the senior move.
The Fine-Tuning Side

LoRA trains the delta; QLoRA shrinks the base it sits on.

LoRA

Freeze W; learn ΔW = B·A with rank r ≈ 8–64. Trainable params drop ~1000×, optimizer state with them. Adapters merge into W at deploy — zero inference cost — or hot-swap for multi-tenant serving.

QLoRA

Backprop through a frozen 4-bit NF4 base (NormalFloat: quantiles of a Gaussian — matched to how weights are actually distributed), plus double quantization of the scales and paged optimizers. A 70B fine-tune on a single 48 GB GPU.

Memory math callback: full fine-tuning ≈ 16 bytes/param (Adam, mixed precision). QLoRA ≈ 0.5 bytes/param for the base + a sliver for adapters. That ratio is the democratization story.

Worth volunteering: gradients flow THROUGH the quantized base into the FP16 adapters — the base weights never update, so their quantization error is static and the adapters partially learn around it. NF4 detail: information-theoretically optimal for normally-distributed weights (equal probability mass per bin), which is why it beats uniform INT4 for this use. Serving angle: S-LoRA / vLLM batch dozens of adapters over one base model.
Off the Datacenter

GGUF / llama.cpp: quantization as a deployment strategy.

  • Single-file GGUF format: weights + tokenizer + metadata, memory-mapped — model loads lazily from disk
  • Block-wise K-quants (Q4_K_M, Q5_K_S...): per-block scales, mixed precision across layer types
  • Pure C/C++ runtime: CPUs, Apple Silicon (Metal), consumer GPUs, partial offload — no Python, no CUDA required
  • Why it matters in interviews: shows you think about the edge/local regime — where memory is the budget and CPU SIMD does the math
Contrast to complete the picture: TensorRT-LLM sits at the opposite extreme (max datacenter perf, NVIDIA-only), vLLM in the middle (throughput serving), llama.cpp/GGUF at the edge. Ollama wraps llama.cpp for UX. If asked "how would you run a 7B model on a laptop" — GGUF Q4_K_M ≈ 4 GB, mmap'd, Metal/AVX backend — concrete and done.

The One-Breath Answer

"Quantization attacks the memory-bandwidth wall: decode speed ≈ bandwidth ÷ weight-bytes, so FP8 and INT4 double and quadruple the ceiling — FP8's E4M3/E5M2 run natively on tensor cores, INT8 activations need SmoothQuant to tame 100× outlier channels, 4-bit weights need GPTQ's Hessian repair or AWQ's saliency protection, QLoRA extends it all to fine-tuning through a frozen NF4 base, and GGUF carries the same idea to laptops."
