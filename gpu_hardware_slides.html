Framing line to open with: "CPUs are latency machines; GPUs are throughput machines." That one sentence signals you understand the design philosophy split — it's the thesis of the whole deck.
Design Philosophy

CPUs minimize latency per thread. GPUs maximize throughput across thousands.

CPU: few fat cores

8–64 cores. Huge caches, branch prediction, out-of-order execution, speculative execution. Silicon spent making ONE instruction stream fast.

vs

GPU: thousands of thin cores

An H100 has 16,896 CUDA cores across 132 SMs. Minimal control logic per core — silicon spent on raw ALUs. Latency is hidden, not avoided.

name-drops: SM (Streaming Multiprocessor) · SIMT · latency hiding
Key phrase: "GPUs hide latency with parallelism instead of avoiding it with caches." When one warp stalls on memory, the warp scheduler instantly swaps in another — zero-cost context switch because register state stays resident. Contrast: CPU context switches cost microseconds; GPU warp switches cost nothing.
Execution Model

The unit of execution is the warp: 32 threads in lockstep.

This is SIMT — Single Instruction, Multiple Threads. One instruction decoder drives 32 lanes. That's why control logic is cheap and ALUs are plentiful.

name-drops: kernel · grid/block/warp hierarchy · warp scheduler · occupancy
Occupancy = how many warps are resident per SM, which determines latency-hiding ability. Caveat to drop: high occupancy isn't always optimal — register pressure trades against it (cite Volkov's "Better Performance at Lower Occupancy"). Also mention branch divergence here: if threads in a warp take different branches, both paths execute serially with lanes masked off — this is why GPUs hate branchy code.
Memory Hierarchy

Performance is won and lost in the memory hierarchy.

Registers~0 cyc · per thread
Shared Memory / L1~30 cyc · per SM, programmer-managed
L2 Cache~200 cyc · 50 MB, chip-wide
HBM3 (global memory)~400+ cyc · 80 GB @ 3.35 TB/s

Rule: memory coalescing — adjacent threads must read adjacent addresses, or a warp's one memory transaction becomes 32.

name-drops: HBM3/HBM3e · shared memory tiling · coalesced access · bank conflicts
HBM = High Bandwidth Memory: DRAM dies 3D-stacked next to the GPU die on a silicon interposer — that's how you get 3.35 TB/s vs ~100 GB/s DDR5 on a CPU. "Shared memory" is a programmer-managed scratchpad (unlike CPU caches which are hardware-managed) — tiling matmul into shared memory is THE canonical CUDA optimization. Bonus term: bank conflicts (shared memory has 32 banks; two threads hitting the same bank serialize).
The Real Bottleneck
~300 : 1
FLOPs an H100 can do per byte it can fetch from HBM (BF16 dense)

The roofline model: a kernel's arithmetic intensity (FLOPs/byte) decides whether it's compute-bound (matmul) or memory-bound (almost everything else — attention, normalization, elementwise ops). The memory-bound fixes: kernel fusion and FlashAttention.

name-drops: roofline model · arithmetic intensity · memory-bound vs compute-bound · kernel fusion
This is the single highest-leverage concept in a performance interview. Most deep learning ops are memory-bound, which is why kernel fusion (do more math per byte loaded) matters, and why FlashAttention is famous: it restructures attention to be IO-aware, keeping intermediates in SRAM/shared memory instead of round-tripping to HBM (Tri Dao, 2022). Drop "Horace He's 'GPUs Go Brrr' taxonomy: compute-bound, memory-bound, overhead-bound."
Specialized Silicon

Tensor Cores do one thing: small matrix multiply-accumulate, in one clock.

The operation

D = A×B + C on 4×4 (and larger) tiles, fused. CUDA cores do scalar FMA; Tensor Cores do a whole MMA per instruction.

The precision ladder

FP64 → FP32 → TF32 → BF16/FP16 → FP8 → FP4. Each step down ≈ doubles throughput. Mixed precision: compute low, accumulate in FP32.

Google's answer to the same insight: the TPU systolic array — a grid of MACs where data flows through, weights stay put.

name-drops: Tensor Core · MMA · BF16 (invented at Google Brain) · FP8 Transformer Engine · systolic array
BF16 is a Google Brain invention: same 8-bit exponent as FP32 (same dynamic range, no loss-scaling gymnastics), truncated mantissa. H100's "Transformer Engine" dynamically picks FP8 vs FP16 per layer. TPU contrast is a great Google interview move: TPUs are systolic arrays (Kung & Leiserson, 1979 concept) — a 128×128 or 256×256 grid of multiply-accumulate units with data pumped through like a heartbeat; no instruction fetch per op at all.
Why Everything Becomes Matmul

Matmul is O(n³) compute on O(n²) data — the one op that outruns the memory wall.

  • Each loaded tile is reused n times → high arithmetic intensity by construction
  • Tiling into shared memory + registers = the classic GEMM kernel
  • You never write it yourself: cuBLAS / cuDNN, CUTLASS, or compilers (Triton, XLA)
name-drops: GEMM · cuBLAS/cuDNN/CUTLASS · OpenAI Triton · XLA (Google's compiler for TPU & GPU)
This slide answers "why do GPUs crush neural nets specifically?" — because training/inference is ~90%+ GEMM, and GEMM is the rare op whose compute grows faster (n³) than its data (n²), so it can saturate the ALUs. Conv layers are lowered to GEMM via im2col or done with implicit-GEMM in cuDNN. XLA is the Google name to drop: the compiler behind JAX and TF that fuses ops and emits code for both TPUs and GPUs.
Beyond One GPU

At cluster scale, the network is part of the computer.

PCIe Gen5~64 GB/s · host ↔ device
NVLink 4 + NVSwitch900 GB/s/GPU · all-to-all inside a node
InfiniBand / RDMA (or Google ICI for TPU pods)400–800 Gb/s · across nodes

Collectives run on NCCL — ring / tree all-reduce to average gradients without a central bottleneck.

name-drops: NVLink/NVSwitch · NCCL all-reduce · GPUDirect RDMA · TPU pod ICI + optical circuit switching
Ring all-reduce (popularized by Baidu, then Horovod) moves 2(N-1)/N × data per GPU regardless of GPU count — bandwidth-optimal. GPUDirect RDMA lets the NIC DMA straight into GPU memory, skipping the CPU. Google flex: TPU v4 pods use optical circuit switches (OCS) to reconfigure the pod topology — cite the TPU v4 paper (Jouppi et al., ISCA 2023).
Scaling Training

Three axes of parallelism, one memory budget.

Data parallel

Replicate model, split the batch, all-reduce gradients. Simple — until the model doesn't fit.

Tensor parallel

Split individual matrices across GPUs (Megatron-LM style). Needs NVLink-class bandwidth.

Pipeline parallel

Split layers across GPUs; micro-batches fill the pipeline bubble (GPipe — a Google paper).

Plus ZeRO / FSDP to shard optimizer state, and activation checkpointing to trade compute for memory.

name-drops: Megatron-LM · GPipe · ZeRO (DeepSpeed) · FSDP · 3D parallelism
Memory math worth quoting: Adam training in mixed precision costs ~16 bytes/parameter (2 wt + 2 grad + 4+4+4 optimizer states) — so a 70B model needs ~1.1 TB just for states, far beyond one 80 GB H100. That's the "why" behind all of this. "3D parallelism" = combining all three axes (Megatron-DeepSpeed). GPipe is from Google — good to cite in a Google interview.

Signature estimation for interviews: autoregressive decoding reads ALL weights per token. 70B model in FP16 = 140 GB... doesn't fit; in FP8 = 70 GB. tokens/sec/GPU ≈ 3.35 TB/s ÷ 70 GB ≈ ~48 tok/s upper bound, batch=1. The Honest Slide

Knowing when a GPU loses is senior-engineer signal.

  • Branch divergence — warps serialize on divergent control flow
  • Serial dependencies — Amdahl's Law: the sequential fraction caps speedup
  • Small problems — can't amortize kernel launch + PCIe transfer
  • Pointer-chasing — random access defeats coalescing; graphs & trees hurt
  • Overhead-bound — Python/dispatch cost dominates tiny kernels
name-drops: Amdahl's Law vs Gustafson's Law · CUDA Graphs · overhead-bound regime
Interviewers love the counter-question "when would you NOT use a GPU?" Amdahl: speedup ≤ 1/(s + p/N). Gustafson's rebuttal: at scale, you grow the problem instead. CUDA Graphs fix launch overhead by recording a whole DAG of kernels and replaying it. Tie back to the original table: everything on it — pixels, particles, Monte Carlo trials, matrix tiles, dataframe rows — is embarrassingly parallel or tiled-parallel, which is exactly the shape this hardware demands.
The One-Breath Answer

"A GPU trades per-thread latency for massive throughput: thousands of SIMT lanes fed by HBM, kept busy by warp-level latency hiding, accelerated by tensor cores for matmul, and stitched into one computer by NVLink and NCCL."

Say that sentence, then go deep wherever the interviewer pulls the thread. Every noun in it is a slide in this deck.

Call to action: rehearse the one-breath answer out loud, then practice expanding any single noun (SIMT, HBM, warp, tensor core, NVLink, NCCL) into a 2-minute deep dive. That's exactly the shape of a Google systems/domain interview: breadth sentence first, depth on demand.
