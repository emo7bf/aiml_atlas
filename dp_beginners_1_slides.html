What It Actually Is

Two properties make DP work — and they're your recognition test.

Overlapping subproblems

The naive recursion solves the same smaller problem over and over. In fib(5)'s call tree, fib(3) appears twice, fib(2) three times — and it explodes exponentially.

fib(5)
├─ fib(4)
│  ├─ fib(3)
│  │  ├─ fib(2)
│  │  └─ fib(1)
│  └─ fib(2)
└─ fib(3)  ← same work, again!
   ├─ fib(2)
   └─ fib(1)

Optimal substructure

The best answer to the big problem is assembled from best answers to smaller ones. Best way to climb 10 stairs = best way to climb 8 or 9, plus one move. No "global cleverness" needed — small optima compose.

Both present → DP. Overlap missing → plain divide & conquer (mergesort). A provably safe local choice → greedy is cheaper.

The recognition test is the first instinct to install: before writing anything, ask "does brute force re-solve identical subproblems?" (overlap) and "can I build the big answer from small answers?" (substructure). Saying this check out loud at the whiteboard IS structured problem solving — interviewers score it. Counter-example to have ready: longest SIMPLE path in a graph has overlap but NO optimal substructure (sub-paths constrain each other) — DP fails there.
The Instinct — Memorize This Recipe

Five questions solve every DP problem in this series.

QuestionFor Climbing Stairs…
1STATE — "dp[i] = ___" in plain Englishdp[i] = number of ways to reach step i
2TRANSITION — how do smaller states combine?dp[i] = dp[i−1] + dp[i−2] (last move was 1 or 2)
3BASE CASES — smallest states answered directlydp[0] = 1, dp[1] = 1
4ORDER — compute so dependencies come first (or memoize)i = 2, 3, …, n
5ANSWER + COST — where is it? complexity?dp[n] · states × transition = n × O(1) = O(n)

This is SRTBOT (MIT 6.006, Erik Demaine) with friendlier words. Step 1 is where DP problems are won or lost: if you can't say the state in one English sentence, stop and rethink.

Drill ritual: for EVERY problem in this deck (and your own practice), write the five answers before any code. The English-sentence test for state is the single highest-leverage habit: "dp[i] = the number of ways to…", "dp[i] = the max money using houses 0..i". Vague state → wrong recurrence → unfixable code. Demaine's SRTBOT lectures (MIT OCW 6.006, free on YouTube) are the gold-standard deep version of this slide.
Worked Example 1 · Fibonacci

One problem, four speeds — the whole DP story in 14 lines.

# ① naive recursion — O(2ⁿ): re-solves overlapping subproblems
def fib(n): return n if n < 2 else fib(n-1) + fib(n-2)

# ② memoization (top-down) — O(n): the SAME recursion, plus a cache
from functools import cache
@cache                                  # dict keyed by n, filled lazily
def fib(n): return n if n < 2 else fib(n-1) + fib(n-2)

# ③ tabulation (bottom-up) — O(n) time, O(n) space: fill the table in order
def fib(n):
    dp = [0]*(n+1); dp[1] = 1          # base cases
    for i in range(2, n+1): dp[i] = dp[i-1] + dp[i-2]
    return dp[n]                        # answer lives at dp[n]

# ④ space-optimized — O(n) time, O(1) space: only 2 states ever matter
def fib(n):
    a, b = 0, 1
    for _ in range(n): a, b = b, a + b
    return a

The interview arc is always ①→②→③→④: show you see the overlap, cache it, invert it, then shrink it. Memo vs tabulation trade-off: memo is easier to derive; tabulation dodges Python's ~1000-frame recursion limit and unlocks ④.

Color mapping in the code: teal = base cases, rose = the transition — same semantics as the slides. Talking points per step: ① "T(n) = T(n−1)+T(n−2)+O(1) → exponential, ~φⁿ". ② @cache makes each n computed once → O(n) time, O(n) space (cache + recursion stack!). ③ same table, explicit order, no stack. ④ the dependency window is only {i−1, i−2}, so keep two variables — the space-optimization instinct that generalizes to 'keep one row' in 2-D problems (Part 2).
🎛 Interactive · Feel the Explosion

Slide n. Watch why caching isn't optional.

Naive calls ≈ 2·fib(n+1)−1 (exponential, ~1.618ⁿ). Memoized: each state computed exactly once. At n=35 that's the difference between ~30 million calls and 35.

Demo script: n=10 (354 calls vs 10 — noticeable), n=25 (~243k vs 25 — absurd), n=35 (~30M vs 35 — the bar chart gives up). The verbal takeaway: "the state space was always tiny (n states); the naive recursion just refused to notice." That reframe — count the DISTINCT states, not the calls — is the complexity instinct.
Worked Example 2 · Climbing Stairs (LeetCode 70)

"You can climb 1 or 2 steps. How many ways to reach step n?"

Run the recipe

1 · State: dp[i] = # ways to stand on step i
2 · Transition: the last move was +1 or +2, so dp[i] = dp[i−1] + dp[i−2]
3 · Base: dp[0]=1 (one way: do nothing), dp[1]=1
4 · Order: left to right   5 · answer dp[n], O(n)/O(1)

The transferable instinct

The transition came from asking: "what was the LAST decision?" Condition on it, and the rest of the problem is a smaller copy of itself. This one question generates the recurrence for most beginner DP — it's literally Fibonacci wearing a costume, and noticing that out loud is interview gold.

"Condition on the last decision" is instinct #2 (after the English-sentence state test). Variants to mention if probed: steps of 1..k → dp[i] = Σ dp[i−j] for j=1..k (O(nk), or O(n) with a sliding window sum); min COST climbing stairs (LC 746) → same state, min() instead of +, which previews House Robber's max().
Worked Example 3 · House Robber (LeetCode 198)

"Rob houses for max money — but never two adjacent ones."

# 1 STATE: dp[i] = max money obtainable from houses 0..i
# 2 TRANSITION: last decision = rob house i, or don't:
#      rob it   -> nums[i] + dp[i-2]   (forced to skip neighbor)
#      skip it  -> dp[i-1]
# 3 BASE: dp[0] = nums[0]
def rob(nums):
    prev2, prev1 = 0, 0                  # dp[-2], dp[-1] ≡ 0  (space-optimized day one)
    for x in nums:
        prev2, prev1 = prev1, max(prev1, prev2 + x)   # max(skip, rob)
    return prev1                          # 5: answer; O(n) time, O(1) space

New ingredient vs stairs: the transition is now a max over choices instead of a sum over ways. That's the whole difference between counting DP and optimization DP — same recipe, different combiner.

This is the "20-30 lines of clean code" league for Track A — rob() is 5 lines and interview-complete. The counting-vs-optimizing taxonomy: combiner + (count ways), min/max (best value), OR (reachability — e.g., Jump Game). Same 5-step recipe each time; only step 2's operator changes. Follow-up they love: House Robber II (circular street) → run the line version twice: houses[0..n−2] and houses[1..n−1], take the max — reduces the new problem to the solved one.
Two Dialects, One Language

Derive top-down. Ship bottom-up. Know why.

Memoization (top-down)Tabulation (bottom-up)
How it feelswrite the recursion, add @cachefill a table from base cases up
Deriving iteasier — it IS the recurrencemust figure out iteration order
States computedonly the ones actually neededall of them
Recursion limitPython dies ~1000 deep ⚠immune (it's a loop)
Space optimizationhard (cache keeps everything)easy — keep last row / 2 vars
Interview strategyderive top-down out loud → convert to bottom-up → optimize space if asked
The conversion procedure (worth rehearsing once): memoized fn's argument(s) become table indices; base cases seed the table; the recursive calls become table reads; order = ensure reads happen before writes (for 1-D "i depends on i−1, i−2", that's just left-to-right). Python-specific trap: sys.setrecursionlimit exists but a real interview answer is "I'd tabulate to avoid stack depth entirely."
Spotting DP in the Wild

The phrases that should make your DP sense tingle.

Strong signals

▸ "how many ways…" (counting)
▸ "minimum/maximum cost/profit/path…" (optimizing)
▸ "can you reach/partition/form…" (reachability)
▸ decisions in sequence, each constraining the next
▸ brute force is exponential, but n ≤ a few thousand

Anti-signals

▸ a sort + one pass solves it → greedy (intervals, meetings)
▸ subproblems don't repeat → divide & conquer
▸ need actual paths in a graph with cycles → BFS/Dijkstra
▸ n ≤ 20 and weird constraints → maybe brute force/bitmask is fine

The honest tiebreaker: try to state dp[i] in one English sentence. If a sentence exists, DP probably works. If every sentence you try leaks information ("…but it depends which houses I already robbed"), your state is missing a dimension — the #1 beginner bug.

The "state missing a dimension" bug deserves emphasis: when the recurrence seems impossible, the fix is almost always to ADD to the state (e.g., dp[i][holding] for stock problems — a Part 2 preview). Also name the complexity sanity check: if your state space is 10^9, DP won't run — constraints hint at the intended state (n ≤ 1000 suggests O(n²) states are fine).
The Beginner Bug List
  • Base case off-by-one — test dp on the tiniest inputs BY HAND (n=0, 1, 2) before trusting the loop
  • Iteration order violates dependencies — reading dp[i−1] before it's written; in Part 2 this becomes the row/column ordering bug
  • State undersized — the English sentence "leaks" (see previous slide); add a dimension
  • Transition misses a choice — enumerate the last decision's options exhaustively, then combine
  • Answer in the wrong cell — is it dp[n], dp[n−1], or max(dp)? Say it in step 5, not after the bug
  • Python recursion limit — memoized solutions die ~1000 deep; tabulate

Testing ritual for Track A: trace your table on a 3-element input out loud. It catches four of these six bugs and scores communication points while doing it.

This slide doubles as the self-review checklist after writing any DP solution in a mock. The "trace a tiny input out loud" ritual maps directly to Google's expectation that candidates test their own code without prompting — it's the same discipline as the sparse-vector trace from the live interview round.

The One-Breath Answer

"DP applies when a problem has overlapping subproblems and optimal substructure; I define the state in one English sentence, derive the transition by conditioning on the last decision, pin the base cases, pick an order or memoize, and read the complexity as states × work-per-transition — then convert top-down to bottom-up and shrink the table to the dependency window."
